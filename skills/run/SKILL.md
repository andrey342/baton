# /baton:run

Arguments: `$ARGUMENTS`

The plugin's files: `${CLAUDE_PLUGIN_ROOT}` (below, **PLUGIN**). You are the **coordinator**: you propose, and on the person's yes you launch here; each part's implementer session does the work, and `/baton:event` (`PLUGIN/skills/event/SKILL.md`) says what you do each time one ends a turn. Nobody else watches the plan: what you do not write to the run's files is lost when this chat compacts.

A run has three moments (plan 0.3, D1): the **proposal** (steps 1–2, this turn), the **launch** (step 4, the turn of the person's yes, which is what lets the app start sessions) and the **events** (`/baton:event`).

- With a plan path: the proposal (steps 1–2), then end the turn.
- With `--dry-run`: steps 1–2 without writing anything, then say what the launch would do. A dry run creates no branch, worktree, file or session, and never calls `start_session`.
- The person's answer to a proposal (a button or their words, while a run is `proposed`): step 3.
- With no arguments and a run `proposed` in `.claude/runs/*/state.json`: when it holds `proposal.approvedAt` (approved, but the launch stopped), the launch (step 4), since this is the person's turn; otherwise show its table again and ask, as step 2 ends. With a run `running`, `waiting`, `paused` or `closing`: follow "Resuming" in `/baton:event`.
- With no arguments and no open run: look for plans (`docs/plans/*.md`, or the folder the repo's rules name, leaving out `TEMPLATE.md`). Exactly one: offer it in one line ("Run docs/plans/x.md?", with a button when you have `wrap_up`) and propose it on the person's yes. Several: list them and ask which. None: say how to write one (`/baton:plan`).

Rules for every step:

- **No session starts without an approved table.** `start_session` is called only when `state.json` holds `proposal.approvedAt`, written from the person's own yes in this chat. No option, mode, profile key or plan line skips it; the models in the plan and the profile are only where the proposal starts. A 0.2 run (version 1) counts as approved by its own launch (step 4).
- **Work in batches.** Every call costs a full reading of this chat, so calls that do not depend on each other go in one message: the batches below are one message each. If your app asks for a task list and a wrap-up, send `update_plan` inside the first batch and `wrap_up` inside the last, never in a message of their own.
- Talk to the person in the language of the conversation. When the conversation holds nothing from them but the command, take the language of their earlier messages or of their own CLAUDE.md (user memory or instructions in your context); if nothing says, the plan's language (D-41). One line per event unless something needs them. The plan, the brief and the reviews stay in the plan's language; baton's own files in English. The model table and its buttons are in the person's language.
- One shell command per call, never chained with `&&`, `||` or `;`. Write and change files with Write and Edit, never with shell redirections. Use forward slashes in paths.
- Nothing destructive: never `--force`, `-f`, `--force-with-lease`, `-D`, `--delete`, `--mirror`, `reset --hard`, never delete a branch, never remove a worktree with changes, never change the repo's or the person's settings. When a step would need one of these, stop and say so.
- Every state change goes to `state.json` before you end the turn (D-09).
- Nothing runs in the background from this chat: every command runs in the foreground and ends inside the turn. A turn opened by the end of a background task is automated, and the app does not let it start a session (plan 0.3 §2); long work belongs to a part's session.
- The app's tools baton uses (`start_session`, `dismiss_task`, `get_session`, `list_sessions`, `set_session_effort`, `stop_session`, `bind_pr`, `wrap_up`, SendMessage, PushNotification) often arrive deferred: load every one that is listed only by name with a single ToolSearch (`select:<name>,<name>,…`) in the first batch, before deciding you do not have one.

## Files

| Path | Written by | Holds |
|---|---|---|
| `<checkout>/.claude/baton.json` | setup, or the launch | the repo profile |
| `<checkout>/.claude/runs/<run>/state.json` (**runDir**) | you, from the proposal on | the run's state, shaped like `PLUGIN/templates/state.json` (version 2; "State versions" in `/baton:event` for version 1) |
| `runDir/decisions.md` | you, from the approval on | one table row per approval, supervisor decision or escalation |
| `runDir/report.md` | you, at the end | from `PLUGIN/templates/report.md` |
| `<checkout>/.claude/runs/findings.jsonl` | you | one JSON line per finding of a `NO` review, across plans |
| `<worktree>/.claude/runs/<run>/` (**workerRunDir**) | you: `plan.md`, `implementer.md`, `reviewer.md`, `brief.md`, `settled.md`, a `brief-<part>-replan.md` when a part is replanned; each part's session: `result-<part>.md`, `review-<part>-r<n>.md`, `critic-<part>-r<n>.md` | everything the parts' sessions read and write, inside their own folder (D-04, D-15) |

`<checkout>` is `git rev-parse --show-toplevel` of this chat's folder. The worktree is `<checkout>/.claude/worktrees/baton-<run>`. With `workspace: "checkout"` there is no worktree: the run works in the checkout itself, and runDir and workerRunDir are one folder, `<checkout>/.claude/runs/<run>/`.

**Repos.** The profile's `repos` (`name`, `path` from the checkout, `base`, `rules`, `reviewSkills`); without them the run has one repo, `root` at `.`, as in 0.2. Each repo gets a branch of the same name, and each part works in the repos it declares.

## 1. Preflight

**Batch 1**, one message: the ToolSearch above; `git rev-parse --show-toplevel`; `git rev-parse --verify HEAD`; `git status --porcelain`; `git branch --show-current`; Read `.claude/baton.json`; Read the plan file; Glob `.claude/runs/*/state.json`; `date -u +%Y-%m-%dT%H:%M:%SZ`.

1. **Repo.** The two `rev-parse` must pass; otherwise say "baton needs a git repository with at least one commit" and stop. With `workspace: "worktree"`, changes in the checkout are said in one line and never block (the plan works in its own worktree); with `"checkout"` they are step 10's.
2. **Mode.** The launch needs this chat in **auto** permission mode: the implementer session inherits it, and in any other mode it would stop on every dialog. Check it with `mcp__ccd_session_mgmt__get_session` for this session (its `permissionMode`) in batch 2; without that tool, from your context. Not auto: the proposal goes on and says in its last line "switch this chat to auto mode before you approve"; the launch checks again.
3. **Sessions.** Without the app's `start_session` tool (`mcp__ccd_session__start_session`) baton cannot launch: the proposal goes on and says baton needs the Claude desktop app's Code tab to launch; the launch stops there.
4. **Profile.** If `.claude/baton.json` is missing, read the repo as `PLUGIN/skills/setup/detect.md` says (its reads go in batch 2) and keep the detected keys for the launch, which writes them (`roles` only when a repo skill was detected, holding only `skills`, never a default `model` or `effort`, D-39); the proposal says what you found in its options line. Defaults for absent keys: detect.md's table and `PLUGIN/templates/baton.json`.
5. **The plan.** From the file:
   - **Title**: the first `#` heading when it is the only level-1 heading; else the file name.
   - **Options**: the line that starts with `baton:` outside HTML comments, `key=value` pairs: `mode` (`cheap|normal|thorough`), `models` (starting points for implementers, `<part>:<model>[/<effort>]` separated by commas, e.g. `models=B:opus/high,C:sonnet`), `delivery` (`branch|pr|merge|none`), `branch`, `base`. Unknown keys: say them, ignore them.
   - **Already decided**: the section whose heading reads "Already decided", "Ya decidido", "Decided" or "Decisiones".
   - **Parts**: headings that start with `Part`, `Parte`, `Phase`, `Fase`, `Step` or `Paso` followed by an id (a letter or a number) and an optional title after `—`, `-`, `:` or `·`. A heading whose section holds deeper part headings is a container, not a part. Ids must be unique; a plan with no part headings is one part `A`, its whole text.
   - **Criteria** of each part: the list under a heading, bold line or label ending in a colon that says Acceptance, Aceptación, Criteria, Criterios, Done when, Verification or Verificación. A part with none: say it; the reviewer then checks the part's text.
   - **Pauses**: a heading or a line that starts with Pause, Pausa, Stop here, Para aquí, Human decision or Decisión humana marks `pauseBefore` on the next part. A pause that says `deliver: <repos>` (or `entrega: <repos>`) delivers those repos before it stops (a partial delivery, D5): kept as the next part's `pauseDeliver`.
   - **Repos of each part**: a line `**Repos:** backend, frontend` in the part, naming repos of the profile; without it, the analysis of step 2 picks them from the files and folders the part names, and the table shows them. A run with one repo: every part is `root`'s.
6. **Run id.** The plan's file name without extension, lowercased, every run of other characters turned into `-`, cut to 18 characters. The plan's **earlier runs** are the `state.json` files from the Glob whose `plan` is this plan's path (read the latest in batch 2). `proposed`: reuse its folder and id; the new table replaces the old one, with `proposal.revisions` + 1 and `approvedAt` and `words` back to null. `running`, `waiting`, `paused`, `closing` or `done-not-delivered`: the plan is still open (say so, point to `/baton:status`, stop). With `workspace: "checkout"`, the same holds for a run of any other plan in this checkout (step 10). `dry-run` (a 0.2 dry run, version 1) with no commits on its branch beyond its `baseSha`: reuse its id, branch and worktree. Anything else (`delivered`, `stopped`, a 0.2 dry run whose branch got commits): a new run, id suffixed `-2`, `-3`… (the folder is new; the branch is chosen below).
7. **Starting points.** For each role, the profile's `models.start` (a version 1 profile: its `roles`), with `modes.<mode>` laid over it for `cheap` and `thorough`, and the plan's `models=` over that for the parts it names. `inherit` means this chat's model. The proposal starts here and moves away with a reason.
8. **Delivery.** The plan's `delivery=` or the profile's. `pr` becomes `branch` when there is no `origin` remote or `gh auth status` fails (both in batch 2, only for `pr`); say why.
9. **Base and branch.** Decided now, created only at the launch:
   - **Base**, per repo: the repo's own `base` in `repos`, else the plan's `base=`, else the profile's, else the checkout's current branch. Each must resolve in its repo (`git -C <path> rev-parse --verify <base>`, batch 2); failing, say which and stop.
   - **Branch**, the first that applies (D-28): the plan's `branch=`, which must exist locally or as `origin/<branch>`; the branch of the latest earlier run of this plan when it still exists (locally or as `origin/<branch>`) and is **not done with**: not merged into the base (`--merged` prints nothing) or with an open pull request, so an open pull request is updated, never doubled; else the profile's `branch.name` with its markers filled (`PLUGIN/skills/run/hooks.md`), else `<branchPrefix><run>`. When that last one exists already: if `git rev-list --count <base>..<branch>` is 0 reuse it; otherwise stop and say "the branch has work: rename the plan or continue it with `baton: branch=<branch>`".
     The same branch name serves every repo; the checks above run in each repo (`git -C <path> …`), and a repo where the branch has work that is not this plan's stops the launch the same way.
   - **Iteration**: 1 + the number of earlier `runDir`s with the same `branch`; from iteration 2 the options line says it, with the pull request when there is one ("iteration 2 on feat/x, PR #4 open").
10. **Repos and workspace** (batch 2 holds their reads).
   - Each repo's `path` is a repository of its own: `git -C <path> rev-parse --show-toplevel` is that folder. A repo that fails: say which and stop.
   - **`worktree`** (the default) keeps 0.2's single worktree. With more than one repo, 0.3 needs `workspace: "checkout"`: a worktree of the root carries no branch of its submodules. The proposal says so in its options line, and the launch stops.
   - **`checkout`** works in the folder the person uses, which is what Docker Compose project names, code-index tools and absolute paths in MCP configurations need. Two checks:
     - **One open run per checkout.** Another run in the Glob with `workspace: "checkout"` and status `running`, `waiting`, `paused`, `closing` or `done-not-delivered` stops this one: "This checkout already runs `<run>` (<status>): only one run at a time works in a checkout. Finish it or stop it first (`/baton:status`)." Its parts would share the same branches and files.
     - **A clean start.** In each repo, `git -C <path> status --porcelain` prints no tracked change; for the root, add `--ignore-submodules=all` when it holds other repos of the run as submodules (each of those is checked on its own, and their gitlinks are snapshotted at the delivery). A tracked change stops the launch and is named. Untracked files follow `untrackedPolicy`: `stop` (the default) names them and stops; `ignore` names them and goes on; `exclude-local` excludes them in that repo's own exclude file at the launch and takes the lines out again at the close, as `PLUGIN/skills/run/hooks.md` says. A dry run or a proposal reports what would stop or be excluded, and stops or excludes nothing.

**Batch 2**, one message: `get_session` (this chat: its `model`, `effort` and `permissionMode`); Read `PLUGIN/prompts/models.md`; the latest earlier `state.json` of this plan, if any; detect.md and its reads when there is no profile; for each repo (`root` alone without `repos`): `git -C <path> rev-parse --show-toplevel`, `git -C <path> rev-parse --verify <its base>`, `git -C <path> branch --show-current`, `git -C <path> status --porcelain` (checkout only; the root's as step 10 says), and for each candidate branch of step 9 `git -C <path> branch --list <branch>` (and `git -C <path> branch --list <branch> --merged <base>`, `gh pr list --head <branch> --state open --json number,url` when an earlier run had it); the `state.json` of every other run in the Glob, for step 10 (checkout only); for `pr`, `git remote get-url origin` and `gh auth status` in each repo.

## 2. The proposal

Analyse every part as `PLUGIN/prompts/models.md` says: its five axes with the plan section that shows each, a row for its implementer, reviewer and Critic (model, effort, skills), a weight and one reason. `sessions: "per-plan"` in the profile keeps one implementer session for the plan: the table then has one implementer model for every row (D3).

**The ceiling.** This chat's model comes from `get_session` (without it, from your context). An implementer row on a model above it cannot be launched from this chat (the app ignores the request): mark that row "cannot be launched from this chat (<this chat's model>)", and say in the Coordinator line the two ways out, a chat on that model or a lower row. Reviewers and Critics have no ceiling (D-61).

**The table**, in the person's language, one row per part, plus a row "Closing" when the profile's `closing` is not empty:

```text
| Part | Implementer   | Reviewer (skills)       | Critic    | Weight | Reason |
| A    | Sonnet medium | Sonnet medium (—)       | —         | S      | Steps the plan prescribes; a mistake is cheap (Part A) |
| B    | Opus medium   | Opus high (repo-review) | Opus high | L      | Authorization and a public contract (§3, Part B) |
Weight: B is ~70 % of the plan; Sonnet high on B would save ~35 %.
Coordinator: this chat (Opus 5.5). It can launch every row.
Options: delivery pr · publish without asking (the repo asks for a PR) · archive verified sessions: no · iteration 1 on baton/x from main
```

With more than one repo the table has a **Repos** column after Part (the part's repos, from its `**Repos:**` line or from the analysis, marked "(analysis)" then), and a line under the table gives each repo's branch and base: "Branches: `baton/x` in root from `main` · backend from `develop` · frontend from `develop` · workspace checkout". Every reason cites the plan section it rests on. The options line holds the delivery (and its order, `deliveryOrder`, when the run has several repos), publishing as the profile's `humanBeforePublish` says (`false`: without asking; `true`: ask before each publish; `"ask-once"`: one question listing everything; nothing to say for `branch` or `none`), archiving sessions (no unless the person says), the branch and base, the repo's hooks by name with who runs each, and who creates the branches when it is not baton, and what step 1 found that the person should know (no profile yet, the mode, the app). Then the two buttons, through `wrap_up` (its question "Launch with this table?"), or as two lines of text without it: «Yes, launch each part in its session with this table» and «I want to change something», in the person's language (in Spanish, «Sí, lanza cada parte en su sesión con esta tabla» / «Quiero cambiar algo»).

**Batch 3**, one message, only without `--dry-run`, all with Write and Edit:

- `<common-dir>/info/exclude` (`git rev-parse --git-common-dir`, batch 2) holds `/.claude/worktrees/` and `/.claude/runs/` (Edit to add what is missing, or Write it if absent);
- `runDir/state.json`, version 2, `status: proposed`: the run's fields (`run`, `plan`, `title`, `mode`, `workspace`, `sessions`, `checkout`, `runDir`, `iteration`, `gates`, `install`, `reviewRounds` (the profile's, else the template's 3), and `delivery` as the template's object: `mode`, `why`, `order` (the repos in `deliveryOrder`), `repos` and `partial` empty), `coordinator` (`sessionId`, `model` and `effort` of this chat), `repos` with every repo (`path`, `branch`, `base`, and `baseSha` null until the launch), every part's `repos` and `pauseDeliver`, `proposal` (`revisions`: 1, or the earlier proposal's + 1; `approvedAt` and `words` null), every part with its `implementer`, `reviewer` and `critic` rows (`model`, `effort`, `skills`, `reason`), `weight`, `pauseBefore` and `status: pending`, `current` null, `messagesSinceUser` 0, `wakesSinceUser` 0, `presses` with `{ "at": <now>, "what": "proposal" }`, `startedAt` and `updatedAt`;
- the table, the buttons and the `wrap_up`.

Then end the turn: nothing is created until the person answers. With `--dry-run`: no batch 3; show the table, then what the launch would do (each repo's branch from its base; the worktree path, or in a checkout "no worktree: the branches are made in the checkout, `git -C <path> switch -c <branch> <base>` in each repo"; the brief; and the `start_session` call of step 4 with the first part's row), what step 10 would stop on, and that `/baton:run <plan>` proposes it for real.

## 3. The person's answer

Any message the person writes while the run is `proposed` is their answer; read `state.json` and the time (`date -u +%Y-%m-%dT%H:%M:%SZ`) in one message first.

- **A yes**: the approve button, or words that accept the table as it stands ("sí", "lanza", "adelante", "yes", "go"). Write `proposal.approvedAt` (now) and `proposal.words` (their words verbatim), a `presses` entry `approve`, and `runDir/decisions.md` with the header `| When | Part | Stop | Decision | Why |`, its separator line and a row `| <now> | — | proposal | table approved (revision <n>) | <the rows in one line: A sonnet/medium, B opus/medium + critic…> |`. A row still marked as above this chat's ceiling is not approved: say so again and stop. Then the launch, in this same turn.
- **A change** ("baja P3 a Sonnet", "Critic en B", "delivery pr", "otra vez con Opus para todo"): apply it to the rows, recheck the ceiling, recompute the weight line, add 1 to `proposal.revisions`, a `presses` entry `change: <their words>`, Write `state.json` whole, and show the new table with the same buttons. Nothing starts.
- **A stop** ("para", "déjalo", "cancel"): `status: stopped`, and say nothing was created.
- **Unclear**: ask in one line which it is.

## 4. The launch

**The gate, before anything else:** `state.json` must hold `proposal.approvedAt`. Without it, stop: the table is not approved, so go back to step 2. A version 1 run (baton 0.2) counts as approved by its launch ("State versions" in `/baton:event`): when "Resuming" restarts its lost session, only batch 7 runs, with `worker.model` and `effort`, and no table is asked for. Nothing else skips the gate, and a new launch never does. This turn must be the person's own (their yes), auto mode must hold (`permissionMode`, step 1.2) and `start_session` must be loaded (step 1.3); failing either, say it in one line and stop, leaving the approval written.

**Batch 4**, one message: the profile's Write when step 1.4 kept one; `git rev-parse --verify <base>`, and for an existing branch `git merge-base <base> <branch>` and `git rev-parse <branch>`; Read `PLUGIN/templates/brief.md`, and `PLUGIN/skills/event/SKILL.md` unless its text is already in this conversation (batch 7 starts the session as it says, and every event after the launch follows it); Read `PLUGIN/skills/run/hooks.md` when the profile has `hooks`, a `branch.createdBy` other than `baton`, or `untrackedPolicy: "exclude-local"`; the worktree:

0. **The repo's process first**, when `hooks.md` applies, in this order, before any branch: the `exclude-local` lines (and the clean check again); `state.repoRunId` and every marker's value; `onStart` when it is the coordinator's (one command, its row in `decisions.md`). With `branch.createdBy: "hook"`, the check that each repo now has the branch replaces making it below; with `"part:<id>"`, no branch is made here.

1. **Checkout** (`workspace: "checkout"`), instead of the worktree. Check step 10 again (another open run, a clean start). Then, in each repo, one command each: a new branch `git -C <path> switch -c <branch> <base>`; a branch this plan already has (step 9) `git -C <path> switch <branch>`. Never with `--force` or `--discard-changes`. `baseSha` per repo: the base's commit for a new branch, `git -C <path> merge-base <base> <branch>` for an existing one. A switch that fails stops the launch with git's message; say which repos were already switched (their branch stays; `git -C <path> switch <base>` takes each back).
1. **Worktree**: when the branch is already checked out in an earlier baton worktree (`git worktree list --porcelain` shows it under `.claude/worktrees/baton-…`), use that worktree as it is. Otherwise, from the checkout: `git worktree add -b <branch> .claude/worktrees/baton-<run> <base>` for a new branch, `git worktree add .claude/worktrees/baton-<run> <branch>` for an existing one. A failure (the branch checked out elsewhere, a path in use) stops the launch with git's message. `baseSha` is the base's commit for a new branch, and `git merge-base <base> <branch>` for an existing one, so the run's commits are the branch's own (D-34).
2. **Install**: the profile's `install` runs inside the implementer session as the first step of the first part (the brief says so), not here: that keeps the launch in this turn, where the session may be started (D-16).

**Batch 5**, one message, all with Write and Edit (Write creates the folders):

1. **settled.md** in workerRunDir (`<worktree>/.claude/runs/<run>/`), with the line `# Settled while the plan ran` (D-37).
2. **brief.md** in workerRunDir, from `PLUGIN/templates/brief.md` with every `{{…}}` replaced ("Filling the brief" below), one brief for the whole plan. Check your text before writing it: no `{{` may be left.
3. **state.json** in runDir, written whole: `status: running`, `worktree` (null in a checkout), `workerRunDir`, each repo in `repos` with its absolute `path` (in a worktree, the root is the worktree), `baseSha`, and `createdBy` (`baton`, `hook` with its `branchSha`, or `part:<id>`), `repoRunId`, `excluded`, and `hooks`, `branchCreatedBy` and `untrackedPolicy` copied from the profile (the hooks as it writes them; their markers are filled each time one runs) when `hooks.md` applied, the first part `working` with `startSha` one commit per repo of the part (`{ "root": <baseSha for a new branch, the branch's tip for an existing one>, … }`), `current` the first part, a `presses` entry `launch`, and everything the proposal wrote kept as it is.

In a checkout, batch 5 also checks that the run folder is excluded in each repo it lives in (the root's `info/exclude`, batch 3), so `git status` stays clean.
