# baton — decisions

D-01 to D-14 were fixed when the design was chosen; D-15 to D-46 came up while building and testing v0.1, D-47 to D-57 in 0.2 and D-58 onwards in 0.3, each with what changed and why. The live tests ran in two throwaway repos, `baton-demo` (no rules) and `baton-lab` (rules, a repo skill, a `deny`, pull requests). The plan, the per-phase evidence and the final report that these entries cite are kept out of this repository; the README sums up the results.

## Fixed when the design was chosen (2026-10-17)

- **D-01 · Name `baton`**, chosen by the person among English alternatives. Commands `/baton:run`, `/baton:plan`, `/baton:setup`, `/baton:status`.
- **D-02 · Design A:** one coordinator (the chat) and one implementer session per plan, reused through messages. Alternatives B (one session per part, all created at launch) and C (everything inside the chat's own session) are described in `DESIGN.es.md`; B may come later as `fresh=true`.
- **D-03 · The reviewer is a subagent of the implementer session**, not of the coordinator: no message per round, and the gates run in the worktree. Freshness comes from the new context; independence from a fixed prompt in the plugin that reads the plan and the diff by itself, to which the session passes only facts (part, start commit, round).
- **D-04 · Each writes in its own tree.** The implementer session writes results and reviews in `<worktree>/.claude/runs/<run>/`; the coordinator writes the state, decisions and report in `<checkout>/.claude/runs/<run>/` and copies the worktree's folder at delivery. This avoids writes outside a session's folder, which in auto mode may ask for a permission.
- **D-05 · The supervisor is the coordinator**, following `prompts/supervisor.md`: it already holds the plan and costs no extra process. Every decision carries its reason in `decisions.md` and one line in the chat.
- **D-06 · Publish without asking when the repo asks for it** (the person's decision), unless `humanBeforePublish`. If the branch already has an open pull request, the push updates it and the report goes as a comment.
- **D-07 · Default models:** implementer `inherit` (the coordinator's model) with effort `high`; reviewer `sonnet` with effort `medium`. The profile's `cheap` and `thorough` modes change them per plan (`baton: mode=…`).
- **D-08 · One press launches the plan:** the person's sentence. No confirmation dialog: the skill says in one line what it detected and what it will do, and starts.
- **D-09 · State lives in files** (`state.json`, briefs, results, reviews, decisions), never only in the chat's memory. Reopening the app and saying "sigue" is enough.
- **D-10 · Message quota:** a counter in `state.json` and a stop with a button. Set by measurement in D-33.
- **D-11 · No code and no hooks in the plugin:** only skills, an agent, prompts and templates. Anything that needs code (counting tokens, say) is an optional script whose absence breaks nothing.
- **D-12 · Installation:** `claude plugin marketplace add andrey342/baton` and `claude plugin install baton@baton --scope user|project`, run by the chat from one sentence. In tests, project scope in the test repo with `.claude/settings.json` committed, so the worktree's session loads the plugin; after a change, uninstall and install again (or bump the version) to refresh the cached copy.
- **D-13 · Language:** text for the person in the language of their conversation; the plan and the reviews in the plan's language.
- **D-14 · Nothing destructive by default:** no `--force`, no deleting branches or worktrees with changes, no changes to the repo's or the person's settings.

## v0.1 Phase 1 (2026-10-17)

**D-15 · The implementer session reads only files inside its own folder.** At launch the coordinator copies into `<worktree>/.claude/runs/<run>/` (workerRunDir) the plugin's `prompts/implementer.md`, `agents/reviewer.md` and the plan file (`plan.md`), and writes the briefs there. The brief and the reviewer prompt point at those copies, so the brief's `{{pluginRoot}}` and `{{planAbs}}` placeholders are gone (replaced by `{{workerRunDir}}` and `{{planCopy}}`). Why: the plugin lives in a cache folder outside the worktree, and a read there from a session in auto mode may ask for a permission nobody answers (D-04's reasoning, applied to reads); a plan the person has not committed is not in the worktree at all, and the reviewer must read the plan as launched.

**D-16 · The install command runs inside the implementer session, as the first step of part A.** The original design had the coordinator run it in the background. A background job ends in a later turn that is not the person's, where `start_session` is refused (limit 1); running it in the foreground would hold the launch turn for up to ten minutes. The brief gains `{{install}}` ("none" for parts after A), and an install that fails is a `blocked` result with its last lines.

**D-17 · Briefs are written once, in workerRunDir.** The original design had the master brief in the checkout's run folder and a copy in the worktree. One file is one source; the coordinator writes it inside its own cwd (the worktree is under the checkout), and at delivery the whole workerRunDir is copied into runDir, so the briefs end up there too.

**D-18 · The implementer's final message is the `baton-result` block alone; a `wrap_up` recap starts with `baton-result: <status> · part <X>`.** The app wakes the coordinator with the first 400 characters of the session's report (its wrap-up recap, then its final message). With the status in those characters the coordinator can tell a stale `result-<part>.md` from a fresh one without timestamps; the file stays the full record.

**D-19 · Fixed message prefixes to the implementer.** Every message the coordinator sends starts with `baton ·` and one of: `part <X>: read and follow <brief>`, `part <X> replanned: …`, `answer from the plan for part <X>: …`, `answer from the person for part <X>: …` (verbatim), `retry part <X>: …`, `continue part <X> from your brief …`, `part <X>: end your turn with the baton-result block …`, `part <X> is not reviewed OK yet: …`. `implementer.md` lists them, so the implementer knows what each asks without the coordinator explaining.

**D-20 · The implementer never messages the coordinator or starts sessions.** A session started by another session is told by the app it may send one question with SendMessage. baton's channel is the result block only, so the stop, the question and the counters stay in files; a message that arrives anyway is read as a `question` result.

**D-21 · The run id is the plan's file name, kebab-cased and cut to 18 characters.** The app's session `name` takes `[a-z0-9-]`, at most 24 characters, and baton names the session `baton-<run>`. A finished run (`delivered`, `stopped`) of the same plan gets `-2`, `-3`…; a `dry-run` is reused, with its worktree, while its branch has no commits beyond its base (D-28); an open one (`running`, `waiting`, `done-not-delivered`) refuses a second launch.

**D-22 · A dry run creates the branch, worktree, exclusion, state and first brief, but runs no install and starts no session.** It writes `status: dry-run` and the `start_session` call it would make. The next real `/baton:run` of the same plan reuses the worktree and branch; an existing default branch is reused only when it has no commits beyond the base, so a dry run never collides with real work.

**D-23 · The profile is sparse and `isolation` is gone.** `setup` writes only detected keys (criterion 2); every default lives in `skills/setup/detect.md`'s table and `templates/baton.json`, which now shows the defaults (`branchPrefix: baton/`, `delivery: branch`, empty `gates` and `install`) instead of an example repo. baton v0.1 always works in a worktree, so the `isolation` key had nothing to choose.

**D-24 · Detection lives in `skills/setup/detect.md`, shared by `setup` and `run`.** One reading of the rules for both; `run` reads it only when the repo has no profile. A supporting file is not a skill and gets no `${CLAUDE_PLUGIN_ROOT}` substitution, so it names other plugin files by role and the skill that loads it gives their paths.

**D-25 · State fields added:** `run`, `gates`, `install`, `reviewRounds`, `delivery` as an object (mode, why, URL, worktree outcome), per-part `endSha`, `decisions`, `retries`, `replanned`, plus `lastSentAt` and `presses` (one entry per thing the person did, for the report's "What needed you"). Statuses: `dry-run`, `running`, `waiting`, `done-not-delivered`, `delivered`, `stopped`. Why: the supervisor's limits (six decisions, two retries, one replan per part) and the message count must survive a compaction (D-09).

**D-26 · The reviewer may use PowerShell, and its frontmatter description is a YAML block scalar.** On Windows a gate may only run through PowerShell; the agent's `tools` adds it and the prompt says to try the other shell once if one refuses. Descriptions with `: ` inside broke YAML parsing, and `claude plugin validate` does not parse skill frontmatter (it checks agents only), so every description is a `>-` block and the Phase 1 evidence parses them separately.

**D-27 · `/baton:status` reports without acting.** Only `continue` and `stop` (or "sigue", "para") change anything; `continue` follows the run skill's step 8, so resumption has one description. foreman's D-109 taught that a status answer must not open or message sessions on its own.

## v0.1 Phase 1 review fixes (2026-10-17, review round 1)

**D-28 · The same plan goes back to its same branch (review H-1).** Running a plan again after a delivery used to give run `-2` and branch `<prefix><run>-2`, so a second pull request, against the person's decision that an open pull request is updated (D-06). Now the run folder still gets `-2` (folders never collide), but the branch is the latest earlier run's when that branch still exists and is not done with: not merged into the base (`git branch --list <b> --merged <base>` empty) or with an open pull request (`gh pr list --head <b> --state open`). Only a merged or vanished branch gives a new `<prefix><run>`. `iteration` counts the runs on that branch and is said in the launch line with the pull request. When the branch is still checked out in an earlier baton worktree (a dry run, a stopped run), that worktree is used as it is, since git refuses a second checkout of one branch. A dry run is reused only while its branch has no commits beyond its base; once someone has worked on it, it counts as an earlier run. `baton: branch=` stays for the exceptional case of another branch.

**D-29 · A verdict is the first non-empty line, `Verdict:` or `Veredicto:` (review O-1).** The coordinator and the implementer read the first non-empty line of a review, past a code fence, and accept the Spanish label, so a reviewer's stray blank line does not cost a message of the quota. The reviewer is still asked for `Verdict:` in English on the very first line, whatever the review's language.

**D-30 · App tools are loaded with ToolSearch, and auto mode is checked with get_session (review O-2, O-3).** `start_session`, `get_session`, `stop_session`, `bind_pr`, `wrap_up` and PushNotification often arrive deferred; `run` and `status` say to load one with `ToolSearch select:` before concluding it is missing. The preflight reads `permissionMode` from `get_session` for this session, and falls back to the context only without that tool.

**D-31 · `setup` warns that `settings.local.json` does not reach the worktree (review O-4).** A plan's worktree holds only committed files, so `permissions.deny` or `enabledPlugins` set only in `settings.local.json` do not apply in the implementer session. `setup` says so in one line when it finds them; the README will too (Phase 4).

**D-32 · A coordinator inside an app worktree nests baton's worktree in it — kept for v0.1 (review O-5).** From `<repo>/.claude/worktrees/<x>`, `--show-toplevel` is that worktree, so baton's lands at `<x>/.claude/worktrees/baton-<run>` and its run folder under `<x>/.claude/runs/`. It works. Moving both next to the main checkout (from `--git-common-dir`) would put the coordinator's writes outside its own folder, which in auto mode may ask for a permission, and would split the run from the chat that owns it; that trade is left for 0.2, after Phase 2 shows how the app's own worktree clean-up treats baton's (review O-6).

## v0.1 Phase 2 (2026-10-17, live round 1 in baton-demo)

**D-33 · Limit 2, measured: 10 messages to other sessions per message the person writes in the sending session (adjusts D-10).** Measured by the coordinator on 2026-10-17: the 11th `SendMessage` returns "Not delivered: this session has already messaged Claude Desktop sessions 10 times since your user last typed here… Paused until your user's next message in this session". Only the person writing in that same session resets it; `<side-sessions-event>` wake-ups from other sessions do not. baton's counter stops before the message that would make it 10: at most 9 go out between two words from the person, and one stays in reserve, so the coordinator is never refused mid-plan. A plan spends one message per part plus one per answer or retry; demo used 4 in all, with a peak of 2 between presses. The README will say that a long plan with no pauses or escalations asks for a word after nine messages (Phase 4).

**D-34 · Small fixes from the live round (Phase 2 P3).** `state.delivery.worktree` now always says what happened to the worktree (`removed`, `removed; its empty folder stays while the implementer session holds it`, or `kept: <why>`); in demo-fix it stayed `null` while the report said "removed". For an iteration on an existing branch, `baseSha` is `git merge-base <base> <branch>`, not the base's current head: demo-fix took `main`'s new commit (the plan itself) as its base. The report lists `baseSha..<branch>`, the commits a pull request would show, and marks those older than the first part's `startSha` as earlier iterations.

**D-35 · Known limitation: empty worktree folders stay while their implementer session lives.** On Windows `git worktree remove` unregisters the worktree but cannot delete a folder that a live process uses as its cwd (foreman D-139). baton leaves the session alive (archiving it is the person's call), so `.claude/worktrees/baton-<run>/` stays as an empty, git-excluded folder until that session ends; the state and the report say so. Removing it later is safe (`Remove-Item` or `rmdir` on an empty folder). The README will list it (Phase 4).

**D-36 · `/baton:run` with no argument and no active run offers the repo's plan (Phase 2 review O-3).** The live round showed the model already doing it; now it is written: one plan in `docs/plans/` (or the rules' folder, `TEMPLATE.md` left out) is offered with a button and launched on the person's yes, which is still their turn, so the session may be started; several are listed; none points to `/baton:plan`.

## v0.1 Phase 3 (2026-10-17, live round 2 in baton-lab)

**D-37 · Answers are written to `settled.md` in the implementer's run folder (Phase 3 P2).** In baton-lab the reviewer of part A could not confirm the person's choice ("numbers only"): answers travelled only in the message to the implementer, and the reviewer reads the plan and the run folder. Now the coordinator appends every answer, from the plan or from the person, to `workerRunDir/settled.md` (time, part, source, question, answer verbatim) before sending it; the brief, the implementer prompt and the reviewer prompt name it, and "Already decided" plus `settled.md` are what counts as decided. The report lists it. The test session had improvised the same thing as a "Settled during part A" section in brief-B.

**D-38 · A new pull request's body is the final report (Phase 3 P3).** PR #1's body was the report as it stood at `gh pr create`, before the coordinator added the URL and the worktree's fate. Delivery now removes the worktree before writing the report, and after `gh pr create` puts the URL in and runs `gh pr edit <n> --body-file report.md`. An existing pull request gets the report, URL included, as a comment. A failed publish leaves `done-not-delivered` with the branch intact; the worktree is no longer kept for a retry, since the retry needs only the branch.

**D-39 · The profile never holds a role's default model or effort (Phase 3 P3).** The first run in baton-lab wrote `roles.implementer.model: inherit`, `effort: high` and the reviewer's defaults next to the detected skills. `run` and `detect.md` now write only `skills` under a role; models and efforts stay in `templates/baton.json` unless the person sets them.

**D-40 · Facts from the live round in baton-lab.** The app had already bound the new pull request to the coordinating session when `bind_pr` ran ("already bound"); baton treats that as success. A plan run again from the same file after editing it to one new part went back to `feat/lab` by itself (D-28: not merged, PR #1 open), with `iteration: 2`, the merge-base as `baseSha` (D-34), and a comment on PR #1 instead of a second pull request. `mode=cheap` reached both roles (implementer `sonnet`/`medium` through `start_session`, reviewer `sonnet`/`low` through the Agent tool). The repo's `deny` was not exercised: the implementer never ran `rm`. Seven reviews over both live rounds were OK in round 1 with honest criteria and repo rules, so the NO path (apply a review, round 2) is still untested live.

**D-41 · The person's language when the chat holds only a command (Phase 3 P3).** In baton-lab the test session received only `/baton:run docs/plans/lab.md` and answered the person in English: "the language of the conversation" had nothing to go on. `run`, `status` and `setup` now say: with nothing from the person but the command, use the language of their earlier messages or of their own CLAUDE.md as the context shows it; failing that, the plan's language (the repo rules' for `setup`). The plan, briefs and reviews keep the plan's language (D-13).

## v0.1 final round (2026-10-17/18)

**D-42 · The review loop's NO path, proven by a probe rather than live.** Ten live reviews over three rounds (demo, demo-fix, lab, lab-2, lab-edge) were all OK in round 1, honestly: the implementers met every criterion, including the repo rules carried in `notes`, even with `haiku`/`low`. To test the NO path without forcing a live session, a probe ran the implementer prompt with `claude -p --plugin-dir <baton> --permission-mode auto --model sonnet` in a throwaway repo whose branch already held a commit missing one criterion (a `RangeError` and its test), with a run folder and brief built exactly as `/baton:run` builds them. The `baton:reviewer` subagent returned NO with one P1 finding, unprompted; the implementer fixed it with a test, re-ran the gate, ran round 2 (OK) and ended with `reviews: r1 NO (1 finding); r2 OK` (18 turns, 100 s, 0.31 USD). The coordinator's side of a NO (`findings.jsonl`, repeated-finding rules) stays untested live; the README and the final report say so. Also confirmed in this round: `settled.md` read by the reviewer (D-37), the new pull request's body equal to the final report (D-38), a per-repo `modes.cheap` reaching both roles, and the repo's `deny` applying in auto mode (probe).

## v0.1 Phase 4 (2026-10-18)

**D-43 · No `scripts/usage.mjs` in v0.1.** The plan made it optional (D-11). The final report's token counts came from a one-off reading of the session transcripts (assistant messages' `usage`, de-duplicated by message and request id) and from the results' `reviewer_usage`; the report keeps "see the session's usage" for the implementer. A shipped script would be baton's first code, and the transcript format is the app's, not a contract; it stays for 0.2 if the report should carry the implementer's tokens by itself.

**D-44 · The README states what baton cannot do.** Its Limitations list the launch the person types (limit 1), the 10-message quota (D-33), empty worktree folders (D-35), `settings.local.json` (D-31), permission dialogs seen only in the sidebar, the NO path proven by probe only (D-42), and the folder-marketplace cache. The install sentence names `andrey342/baton`, which works once the repo is pushed; that push is the person's call.

**D-45 · Cost in USD per row, plan and role, and the model advice (Phase 4 review H-1, H-2).** The final report prices every session from its transcript (usage per message, the maximum of each field across the message's lines, cache writes split into 5-minute and 1-hour) with the official table of the `claude-api` skill shipped with Claude Code 2.1.295 (cached 2026-10-06; cache writes 1.25×/2× input). The test coordinators are split by hour into the plans' windows from `state.json`; what falls outside (start-up, follow-ups, the hand-over) is its own row. Five plans: 12.81 USD, 73 % coordinator, 24 % implementer, 3 % reviewer; the reviewer costs 0.04–0.06 USD per round against foreman's 0.4–1.1 USD. The README and the report advise launching from a Sonnet chat and fixing `roles.implementer.model` in the profile, noting that the app never starts a session on a model pricier than the chat's own.

**D-46 · What is designed but not tested live is listed (Phase 4 review H-3).** README and report name it: resuming after closing the app, replan, retries, the stop at nine messages, `humanBeforePublish`, `merge` delivery, and the coordinator's side of a NO review.


## v0.2 (2026-10-18)

**D-47 · Where the coordinator's cost goes, measured per turn.** The v0.1 coordinators (Opus 5.5) spent 0.77 USD per launch on average (5 launches of 10 to 19 API calls) and 0.39 USD per event (13 events of 3 to 13 calls, 8.3 on average). Every call reads the whole chat again, 95K to 217K tokens of which about 75K are the app's own system prompt, so a turn costs its number of calls times the chat's size; the skill's own length weighs little. A typical event spent two or three `update_plan`, one or two `date`, three to six separate `Edit`s of `state.json`, a read of the brief template and the write of the next brief, each in a call of its own. Measured from the session transcripts, turn by turn (a turn opens at each message, command or side-sessions event).

**D-48 · `/baton:event`, a short skill for every turn end, separate from `/baton:run`.** An event is three calls: one message of reads (`state.json`, the result, `git log` since the part's start, one Grep for every round's verdict and its findings' headings, the time), one message of writes (`state.json` whole, the message to the implementer, the rows of `decisions.md`, `settled.md` or `findings.jsonl` it needs) and one line to the person. `update_plan` and `wrap_up`, when the app asks for them, ride in those batches. `run` keeps only the launch, resuming moves to `event`, and `/baton:status continue` points there. `supervisor.md` is read once, the first time a stop is not `done`.

**D-49 · One brief per plan (replaces D-17's brief per part).** The launch writes `brief.md` with every part, its text and its criteria. Each message to the implementer names the part and its start commit (`baton · part B from <sha>: read and follow brief.md`), and the implementer passes that commit to the reviewer. An event no longer reads the template nor writes a brief; a replan still writes `brief-<part>-replan.md`.

**D-50 · The launch in batches.** Seven messages instead of one call per check: tools and first reads; templates, the earlier run and branch checks; the worktree; the writes (exclusion, `settled.md`, `brief.md`, `state.json`, `decisions.md`); the copies; `start_session`; the worker's id. Deferred app tools are loaded with one ToolSearch in the first batch.

**D-51 · Delivery and report in `skills/event/deliver.md`, read with the last part only.** Gather in one message (copy the run folder, the commits, the results, the reviews' Grep, the findings, the merge or pull-request checks), remove the worktree, write the report and the state in one message, publish, close. A merge is `git merge --no-ff --no-edit`: without `--no-edit` a merge commit may open an editor in a session without a terminal. After a publish question, the person's answer goes into the report's "What needed you".

**D-52 · A replan after exhausted review rounds is the supervisor's, and rounds are numbered across it.** A part blocked because its rounds ran out is replanned once with the profile's number of rounds again, numbered on (r2 after r1), so no review file is overwritten and the `NO` stays for `findings.jsonl`. The supervisor prompt says this is not "more review rounds than the profile", which is the person's.

**D-53 · Fixes from the CLI probes.** Each `NO` round is logged to `findings.jsonl` once, tracked by the part's `logged` round, whether the part ends `done` or `blocked` (the probe logged it at the replan). A message the app refuses (its quota, or a session it cannot reach) makes the coordinator write the state again without it and escalate, since the state is written in the same batch as the message. Any word from the person, a "sigue" included, resets `messagesSinceUser` before anything else (the probe's resume left it at 2 instead of 1).

**D-54 · CLI probes before the live round.** In a copy of the throwaway lab repo, with `claude -p --permission-mode auto --model sonnet` and the plugin at project scope, one conversation ran: the dry-run launch of a two-part plan (6 calls), a simulated `done` event (4 calls, the skill's load included), a `blocked` part after a `NO` review with one round allowed (3 calls: `supervisor.md` read, replan brief, decision row), the last part `done` with `humanBeforePublish` and `merge` (4 calls: worktree removed, report, publish question), the person's "Publish" (4 calls: `git merge --no-ff --no-edit`, delivered), a second plan's dry-run launch (5 calls), an install failure with nine messages sent (3 calls: retry decided, message held, quota question), the person's "Continue" (3 calls: the held retry sent, count at 1) and "sigue" with a result whose event never came (4 calls: the result's time against `lastSentAt`, next part). Simulated events cannot send messages, so the probes check the skills' reading, deciding and writing; what only the app shows (wake-ups, buttons, the quota's real refusal, closing the app mid-part) is for the live round.

## v0.2 live round (2026-10-18 to 10-21, baton-v02-lab)

**D-55 · The reviewer runs with `run_in_background: false`.** With Haiku/low the implementer called the Agent tool without it; the app ran the reviewer in the background, the turn ended before the verdict, and every part woke the coordinator twice. Opus and Sonnet had waited on their own in v0.1. `implementer.md` and the brief now say it.

**D-56 · The app wakes a chat at most 10 times in a row without a word from the person.** Seen twice in t2: after ten wake-ups the eleventh turn end was never delivered, and the run stopped in silence with the part done and its result written. The coordinator counts wake-ups in `wakesSinceUser` like messages (D-33) and asks for a word on the tenth; "sigue" picks up a result written after `lastSentAt` (D-48's resuming), which is how both stops were recovered.

**D-57 · Live results.** Seen working in the app: a retry after a transient install failure, the coordinator's side of a NO (findings logged, replan, round 2 OK), a rule proposed from a finding repeated across two plans, `humanBeforePublish` with `merge` delivery, and resuming after a lost wake-up. Not seen live: resuming with the implementer cut mid-part by closing the app, and the stop at nine messages (the person's words reset the count first; the CLI probe covers it). Coordinator cost with Opus 5.5: 0.20 USD and 3.1 calls per part event against 0.39 and 8.3 in v0.1.

## v0.3 (2026-10-26)

The design is the plan `docs/PLAN-0.3.es.md` (D1 to D14). Points 1 to 4 of its §2, what the app was not yet known to do, were measured in part 1 from the app's own records of MSG's manual Phase 3 and of the earlier baton and foreman rounds (the transcripts under `~/.claude/projects` and the desktop app's session files, read only) and with CLI probes as in D-54.

**D-58 · Schemas v2: profile, state and result block, with v1 still read (part 1).** `templates/baton.json` v2 holds every key of the plan's §4 with its default: `workspace` `worktree`, `sessions` `per-part`, `branch` (`name` null = `<branchPrefix><run>`, `createdBy` `baton`), `repos` empty (one implicit repo `.`), `untrackedPolicy` `stop` (checked only with `workspace: checkout`), the seven `hooks` as null, `deliveryOrder` empty (the order of `repos`), `merge` `never`, `humanBeforePublish` `false` (it also takes `true` and `"ask-once"`, which only the person sets; D-06 stays the default), `authority` (`neverDelegate` `ui-design`, `install-software`; `credentials` is never delegated whether named or not), `resources`, `reviewer.neverRun`, `plan.partHeading` and `plan.decided`, `closing`, `localCi`, and `models.start`, the proposal's starting point: the 0.2 defaults (implementer `inherit`/`high`, reviewer `sonnet`/`medium`) move there, `roles` keeps only `skills` (D-39), and `modes` stays as a starting point. `templates/state.json` v2 is the plan's example made whole: `coordinator`, `proposal`, `repoRunId`, `repos` by name, parts with `implementer`, `reviewer` and `critic` rows, `weight`, `uses`, `pauses`, their own `session`, `startSha`/`endSha` per repo and `verified`, plus `authority`, `locks`, `excluded` and `closing`. The archive flag D10 calls `state.sessions[]` lives in each part's and closing session's `session` object, since the top-level `sessions` holds the profile's mode. Run statuses add `proposed`, `paused` and `closing`, part statuses `paused`, and `waiting.kind` `start` and `resource`; `/baton:event` lists them under "State versions" with a v2→v1 table that `event` and `status` read by, and a run is written back in its own version, never upgraded in flight. Until `/baton:run` starts a session per part it keeps writing v1 state; `setup` writes `version: 2`, and a v1 profile reads the same with the template's defaults (its `roles.<role>.model` standing for `models.start`). The result block v2 in `prompts/implementer.md` adds `paused`, `evidence`, `deviations`, `pause`, `pr`, the Critic in `reviews` and a repo before each commit, and keeps `summary` short because the coordinator is woken with 400 characters (D-18, D-49); reading `coord-result` is the coordinator's, in part 3. Probe: `/baton:status` with `claude -p --model sonnet` in a throwaway repo holding this very run's 0.2 `state.json` (`version: 1`, nine parts) reported it in full without errors and left it unchanged (4 turns, 0.21 USD).

**D-59 · Whether `start_session` counts in the 10-message quota: not measured.** In the Phase 3 coordinator's transcript, counted per word of the person: at most 7 SendMessage in one window (no start) and, with starts, 3 starts plus 1 message; never near 10, and no quota refusal in the whole run. The app's own record of the session lists, in `peerReceipts`, 20 receipts that are all SendMessage calls and none of the transcript's 27 starts, which suggests a start is not a message to another session but does not prove the quota ignores it. baton counts each start as one message in `messagesSinceUser` until the live round (part 9) shows otherwise: being wrong costs at most an earlier «Continue».

**D-60 · Whether a card keeps `model` and `effort`: partly measured.** The tool takes `model` and `effort` with `own_initiative`, and a proposal started by id starts "exactly as proposed" (the schema in the app of 2026-10-26). Two cards were started by the person's click in MSG (`task_75dac5e4`, `task_4179be7e`): both had `model` Opus and no effort, from an Opus/high chat, and both sessions ran Opus/high, so keeping and inheriting cannot be told apart; P3's card (Opus/medium) was dismissed unstarted. Seen too: both card-started sessions woke the chat that proposed them ("The session … you started … finished a turn"), so the card fallback of D3 keeps the coordinator's events, although `wake_when_done` cannot be set on a card. D3 stands: the card's text names its model and effort, and the coordinator checks them with `get_session` at the first event; the live round starts a card whose model is below the chat's.

**D-61 · An `opus` subagent from a Sonnet session runs on Opus, and can name its model.** In the app's records, every Agent call asking `opus` from a `claude-sonnet-5-5` session (22, of which 15 `baton:reviewer` reviews with effort medium or high in MSG's Phase 3) has its subagent transcript on `claude-opus-5-5`; Haiku and Opus sessions asking `sonnet` (28) ran on `claude-sonnet-5-5`. A CLI probe (`claude -p --model sonnet`, one Agent call with `model: opus`, `run_in_background: false`) gave the same, with the subagent answering `Model: claude-opus-5-5` from its own system prompt (2 turns, 0.26 USD). So, unlike `start_session`, whose `model` cannot go above the chat's, the Agent tool runs reviewers and Critics above the session's model: the ceiling of D2 applies to implementers only, and D4's `Model:` line, copied by the reviewer from its system prompt, is reliable. Effort is not in the transcripts: not measured.

**D-62 · What else stops a start in an automated turn: partly measured.** The app marks what opened each turn (`turnOrigin`: `human`, `sdk`, `peer`). In the records, ten starts in turns opened by a side-sessions event succeeded (P1, P2, P3, CA, P4, P5 and four closing sessions of MSG's Phase 3), the longest after 7 events in a row without a word from the person; the two refusals were a turn opened by a `task-notification` (MSG P3) and one opened by another session's message (foreman, `peer`). No start was attempted after a compaction inside a chain nor at the tenth wake-up, so neither is measured. The app's own instructions say a start is refused "on a turn that another session's message or an automated event started", except a side-sessions event "right after the user's own turn here (or another such turn)", and that after many events in a row, or after a coordinator turn that was stopped or failed, notes wait for the next turn. baton keeps D-56's stop on the tenth wake-up, treats a stopped or failed turn of its own as breaking the chain, and on any refusal falls back to the card (D3); the live round records whether a compaction breaks it.
